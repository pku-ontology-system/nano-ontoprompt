# ADR 0025：未来的数据底座——DuckDB 替代 Spark，Dagster 作数据中台（方向记录，本次不实现）

> 日期：2026-11-10 · 状态：**方向已定，尚未实现**（等老师把 Dagster 项目的链接转过来）· 相关：[ADR 0024](0024-generic-data-import.md)

## 背景

用户转达的计划：以后数据要集成在一个数据中台上，**用 DuckDB 替代 Spark，配合 Dagster 作数据中台**；Dagster 是老师他们自己开发的，链接稍后给。现在不要求立刻做完，但后续要切过去。所以这一份只记方向，以及现在的代码为了以后好切做了哪些准备。

## 现状（核对过）

- 仓库里没有 Spark 依赖，也没有 Spark 作业；“替代 Spark”目前指的是以后的数据加工不要走 Spark。
- DuckDB 已经在用：实体消歧引擎用它做分块和配对（和 Splink 一样）；通用导入器用它跑计算表的 SQL（`data_import/duck.py`），TPC-H 的数据也由它自带的生成器造出来；DuckDB 1.2 读不了 pandas 3 的 `str` 类型，所以统一经 pyarrow 表注册。
- 数据进本体的入口只有一个：`Bundle`（数据源、表、关系、计算表的 SQL 和列来源、逐步载入的设置）。内置的五份演示、用户上传的文件，都是先变成 `Bundle` 再导入。

## 决定

1. **方向：** 数据加工（清洗、合并、汇总）以后在 DuckDB 上做，由 Dagster 编排和调度；平台不再自己带加工逻辑，只负责“把加工好的表建成本体、做分析”。
2. **不做：** 不引入 Spark；本次不安装 Dagster，也不写中台的接入代码——接口形式没有定，现在写只会写错。
3. **现在就为切换做的准备（已完成）：**
   - 计算表的 SQL 一律写成 DuckDB 方言，原样存进导入记录（`Derived.sql`），并且写明每个输出列来自哪些输入列。以后这些 SQL 可以原封不动搬进 Dagster 的资产里。
   - `Bundle` 是“数据中台 → 本体”的接口。Dagster 资产物化出表之后，只要能给出 表、数据源、列来源，就能走同一条导入路径，不用改本体侧。
   - 血缘用 OpenLineage 事件表达（`POST /api/v2/analysis/lineage/events`）。如果 Dagster 那边能发 OpenLineage 事件，可以直接接；否则写一个适配层，把资产之间的依赖转成事件。
   - 逐步载入（`Replay`）对应中台里“按分区增量物化”：游标在导入记录里，换成分区即可。
4. **等老师给了链接之后要先弄清的事：**
   - 平台怎么拿到物化好的表：读 DuckDB 文件、读 Parquet、还是调中台的接口；数据放在哪（本机文件、对象存储）。
   - 谁来触发导入：Dagster 调度完成后调平台的导入接口，还是平台主动拉取。
   - 增量和回放怎么对应，权限怎么带过去（现在导入用的是发起人的账号）。
   - 血缘以谁为准：中台自己的资产血缘，还是平台导入时画的。

## 切换的步骤（草案）

| 阶段 | 做什么 | 完成的标志 |
|---|---|---|
| 1 | 读懂 Dagster 项目，确定接口形式，写一个“从中台取表 → `Bundle`”的适配器 | 一份中台里的数据能导入成本体，血缘里有中台的资产 |
| 2 | 把内置演示的数据准备搬到 Dagster 资产里，平台只留导入 | 五份演示由中台产出，平台里没有加工 SQL |
| 3 | 上传的文件走中台的接入，增量和调度由中台管 | 平台只剩“导入、建模、分析” |

## 不要照搬 / 存疑

- 这里的做法是按现在能看到的东西推的，Dagster 项目的实际形态可能不同，到时以那个项目为准，这份记录跟着改。
- “DuckDB 够不够用”要看数据量：现在最大的演示是几万行；真上了大数据量，要看单机 DuckDB 的内存和并发能不能撑住，撑不住再谈别的。
