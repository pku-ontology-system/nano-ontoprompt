# ADR 0022：本体建好之后的分析——三个功能照开源项目重写，用一条 OpenLineage 事件流串起来

> 日期：2026-11-09 · 状态：已采纳（第一版，演示数据上跑通；还没有接到平台里的本体）

## 背景

- 老师的意见：在现有成果上多参考开源项目，看“本体建好之后怎么做分析”。调研见 `docs/research/unofficial/OSS_ONTOLOGY_ANALYSIS_SURVEY_2026_11_09.md`（30 个项目）和 `PALANTIR_FEATURES_AND_OSS_ANALOGS_2026_11_09.md`（Palantir 功能对应的开源项目）。
- 调研的结论：多数项目的前提是 RDF / OWL + JVM，而我们的数据在 PostgreSQL 和 FalkorDB 里，所以借鉴方法、自己实现，不引入项目本身。
- 要做的三个最明显的功能（我们现在都没有）：数据健康、实体消歧、数据血缘。要求先用各个项目自带的演示数据展示，再看怎么合到一起。

## 决定

1. **三个功能各照一个开源项目重写**，放在 `backend/app/services/v2/analysis/`：

   | 功能 | 照哪个项目 | 重写了什么 |
   | --- | --- | --- |
   | 数据健康 `health.py` | Great Expectations（Apache-2.0） | 期望的名字、`mostly` 容差、结果字段；pandas 上的执行；约 30 种期望；按数据生成基线套件 |
   | 实体消歧 `resolution.py` | Splink（MIT） | Fellegi–Sunter：分块规则、u 用随机配对估计、先验用确定性规则加假定召回率估计、m 用 EM 估计、词频校正、连通分量成簇、逐对解释；底层同样用 DuckDB |
   | 数据血缘 `lineage.py` | OpenLineage、Marquez（Apache-2.0） | 接收 OpenLineage 运行事件，按事件推出作业和数据集的图、状态、模式、数据质量，再做上下游和影响分析 |

   没有拷贝任何一个项目的源码；演示数据是项目自带的原文件（见 `backend/examples/analysis/README.md`，含来源、许可证、SHA-256，程序加载时核对）。

2. **三个功能合到一起的办法：用 OpenLineage 事件做总线。** `pipeline.py` 让同一个数据集（Splink 的 `fake_1000`）依次走三步，每一步是一个 OpenLineage 作业，写下一对 START / COMPLETE 事件：
   - 读入：输出“原始数据”数据集，带字段模式；
   - 数据健康：输入“原始数据”，**检查结果作为 `dataQualityAssertions` 挂在被检查的原始数据上**（OpenLineage 标准里数据质量就是这样放的），输出“检查报告”；
   - 实体消歧：输入“原始数据”，输出“候选记录对”和“实体”，**“实体编号”列用 `columnLineage` 追溯到参与比较的原始列**，精确率、召回率放在运行的自定义 facet 里。

   这样血缘图不只是画结构：点原始数据能看到哪几条检查没过，点它还能问“改了会影响谁”。三者之间没有互相调用，只通过事件连接，所以任何一个都可以单独用、单独换。

3. **接口和存储**：`/api/v2/analysis/*`（演示数据、健康、消歧、血缘、流水线、运行记录）；两张表 `v2_lineage_events`（事件原样保存，图在读取时推出）和 `v2_analysis_runs`（每次运行的结果），迁移 `0099`。运行和写入需要 editor 角色，查看只要登录；同一时间只跑一个重计算。

4. **页面**：侧栏新增“数据分析”分组：数据健康、实体消歧、数据血缘、流水线演示（`/analysis/*`）。它们是全局页，不依赖“当前本体”，每个页面的“演示数据”卡片标明来自哪个项目、哪个文件、什么许可证。

## 效果（测试里固定的数字，`backend/tests/test_analysis_demos.py`）

| 演示 | 结果 |
| --- | --- |
| Splink `fake_1000`（1000 条，251 个真实人物） | 精确率 ≥ 0.99，召回率 ≥ 0.88（实测 1.00 / 0.90，F1 0.947），约 1.5 秒 |
| Splink 5 万条历史人物（5156 个真实人物） | 精确率 ≥ 0.93，召回率 ≥ 0.78（实测 0.95 / 0.80，F1 0.870），最大一簇 ≤ 100（70），约 12 秒 |
| Great Expectations 出租车样例（1 万行） | 23 条期望里 8 条不通过，每条的不符合行数固定（64、96、1、8、9、9、6、6327） |
| Marquez seed（26 条事件） | 13 个作业、13 个数据集、27 条依赖，全部作业成功 |

词频校正对 5 万条这份很关键：不加时精确率 0.54、最大一簇 630 条，加上后 0.95 和 70。

## 不要照搬 / 存疑

- 这些数字是这套重写在这些数据上跑出来的，**不是 Splink 或 Great Expectations 官方的结果，也没有拿原项目对拍**。对拍要在临时环境里装原项目，需要先问用户。
- 分块规则、阈值是在演示数据上调的（`demos.py` 里写明参照 Splink 教程的哪些设置），换数据要重新调；召回率的上限是“分块覆盖率”，页面上会显示。
- 正则没有超时，只限制了长度（300 字符）；同步执行，5 万条约 12 秒，更大的数据要改成后台任务。
- 目前只能对 `backend/examples/analysis/` 里的演示数据运行，还没有接到平台里的本体。

## 下一步（不在本次范围）

1. **接到本体**：由对象类型的属性（必填、类型、取值集合）自动生成期望套件，对固定数据视图跑数据健康；违规对象链回对象浏览器。
2. **对象归并**：对 Auto Ontology 的候选、对象实例用实体消歧找重复（现在候选只按名称判重）。
3. **血缘连到本体**：来源表和列 → 映射 → 属性 → 规则 / 函数 → 告警 / 决策，影响分析直接回答“改这一列会影响哪些规则和告警”。
4. 和原项目对拍，确认差距。
