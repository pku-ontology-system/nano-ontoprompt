# ADR 0023：把数据健康、实体消歧、数据血缘接到平台自己的本体上

> 日期：2026-11-10 · 状态：已采纳（在 p4int 上用两个本体实测；见“不要照搬 / 存疑”）

## 背景

ADR 0022 做了三个分析功能，但只能跑项目自带的演示文件。它的“下一步”是：对象类型的属性生成期望、对象和类型找重复、血缘连到本体。工厂数字孪生本体（`07dcb4dd`）里就有两对看起来重复的类型（FactoryResource≈ProductionResource，ScheduleItem≈ScheduledItem），一个是手工建的、一个是 Auto Ontology 从同一张表建的，正好拿来验证。

## 决定

三个功能各加一个“本体里的对象”来源，原来的演示来源不变。页面顶部有来源切换，选择记在地址里（`?source=ontology&ontology=<id>&type=<类型>`），所以别处的链接可以直接打开某个类型。

1. **对象怎么读**（`ontology_source.py`）：走和对象浏览器同一个对象查询，权限和属性脱敏照常生效。一页 200 个以内直接读；更多就建一个 1 小时的固定数据视图分页读，最多 10,000 个，超过的截断并在页面上说明。对象变成一张表，第一列 `__object_id`；对象和数组转成 JSON 文本。

2. **数据健康：期望由类型推出**（`ontology_suite.py`），每条在 `meta.source` 里写明来源：
   - 类型下至少有一个对象；
   - 标识属性非空且唯一（优先用 Auto Ontology 候选记录的主键，没有就按名字推断）；
   - 必填的属性不为空；
   - 属性类型：整数、数字、布尔、字符串按 JSON Schema 检查，时间类的能被解析；数组和 JSON 不检查；
   - 属性定义里写明的 `enum`、`minimum` / `maximum`、`pattern`、`unique`；
   - 外键（声明的或 Auto Ontology 推断的）的取值必须是被指向类型里已有的键（目标对象多于 2000 个时不检查）。
   可以另外加上“按现有数据生成的基线”，标为“数据现状”。不合格的对象编号写进结果，页面上一点就能在对象浏览器里打开。新增了 `expect_column_values_to_match_json_schema` 这一种期望。

3. **重复的对象类型**（`ontology_duplicates.py`）：对象类型太少，训练不了匹配模型，所以用一个看得见公式的得分：0.35×名字相似 + 0.35×属性重合 + 0.30×来自同一张来源表。属性重合先去掉类型自己的名字再比（`resource_name` 就是 `name`，`start_at` 就是 `start`）；≥0.7 为“很可能重复”，≥0.5 为“可能重复”。每一对写出理由和建议（保留有对象的那个），只提示，不合并。接口也能拿 Auto Ontology 的候选集去比现有类型（`?candidate_set=`），页面还没接。

4. **实体消歧**（`ontology_resolution.py`）：比较方式从属性自动拟出，并逐条写明理由——名字类用 Jaro-Winkler 分级并做词频校正，日期用编辑距离，邮箱看地址和用户名，地点精确比较；几乎每个对象一个值的文本、近乎全空的、常量、数字和布尔不参与。粗筛规则按“估算会产生多少记录对”筛掉过大的。对象编号做记录编号，所以每一簇的成员都能点开。真实分组列只在名字明确（`cluster` 等）时才用来打分，也可以选“不打分”。

5. **血缘从本体已有的记录生成**（`ontology_lineage.py`）：来源表 → Auto Ontology 候选集（按候选里记下的 `source_field` 画到列） → 对象类型 → 规则（读了逻辑里写明的哪些属性） → 告警 → 处置单，以及在这个类型上跑过的数据健康和实体消歧。图上每个节点带“层”（数据源表、生成、对象类型、规则、告警、处置、数据分析）和“引用”（能跳到对应的页面）。生成是替换式的（事件的 `source` 是 `ontology:<id>`），再生成一次就是当前的样子。
   - **列级影响**：图里多了 `column_edges`；问“改 `FactoryAsset.t50_series` 会影响什么”，答案是规则 T50 温度持续偏高 → 告警的 `peak`、`window` → 处置单的 `reason`。
   - **访问边界**：本体的血缘只通过 `/ontologies/{id}/lineage/*` 读，要求能访问这个本体；通用的 `/lineage/graph`、`/lineage/impact` 不返回它。

6. **流水线**：`POST /ontologies/{id}/pipeline/run` 让一个类型依次做数据健康、实体消歧，并重写这个本体的血缘，两次运行挂在这个类型上。

7. **演示本体**：`backend/scripts/seed_person_master_demo.py` 把 Splink 的 `fake_1000` 走平台自己的路装进来：表结构按 Auto Ontology 交换格式写出 → 作为候选集导入、全部采纳、发布成修订 → 1000 条记录装成 `Person` 对象。候选集的来源如实标成“表结构导入脚本，未使用模型”。邮箱格式约束由脚本直接写进类型定义（平台还没有属性约束的编辑界面）。

## 不要照搬 / 存疑

- **两条链没有连起来。** 工厂本体的规则读的是手工建的 `FactoryAsset`，Auto Ontology 建的 ProductionResource、ScheduledItem、WorkOrder 没有规则也没有对象；血缘只画平台记着的事，所以手工建的类型没有上游，两条链各画各的，靠“重复类型”把它们联系起来。
- **必填几乎都是“可空”。** 对象查询的目录里属性只有类型和是否可空，而 Auto Ontology 的交换格式里 NOT NULL 没有被带进属性定义，所以现在“必填”“取值范围”“格式”这类期望，只有在类型定义里有人写了才会出现（目前只有演示脚本写过）。
- **对象数只数到一页**（200+），精确计数要固定数据视图，选择器里不值得。
- **血缘是生成时的快照。** 本体、规则、告警变了要再生成一次；规则只读逻辑里写明的属性（筛选、序列窗口、证据），不展开关系遍历；处置动作写回对象的那条边没有画（图里不放环）。
- **血缘里的属性名。** 生成时按生成者能看到的类型和属性写进事件，同一个本体里有访问权的人都读得到，包括生成者能看、而他们看不到的属性名（只有名字，没有取值）。要收紧得在读取时按读取者的目录再过滤一遍。
- **重复类型的权重是手拟的**，没有标注数据校准，只在两个本体（共 7 个类型）上看过；大本体上两两比较是平方级的。
- **每次分页读大类型都会新建一个 1 小时的固定数据视图**；多于 10,000 个对象的类型只读前一部分。
- 消歧只出报告，不改本体；怎么合并是以后的事。
