# ADR 0024：通用数据导入——任何表格和文件都走“候选审阅”这条路变成本体，五份演示数据取代写死的场景

> 日期：2026-11-10 · 状态：已采纳（在本机 p4int 上跑通，后端 132 个分析和导入测试、前端相关页面流程测试通过）· 承接 [ADR 0023](0023-analysis-on-platform-ontologies.md)，未来的数据底座见 [ADR 0025](0025-future-data-platform-duckdb-dagster.md)

## 背景

演示时发现四个互相牵连的问题：

1. 本体建模和数据分析没有打通。点“本体演示”只看到一个 `Person`，而本体库里有一大堆本体，两边对不上。
2. 数据源导入是为某个场景写死的：时序、多模态只能装工业数据，业务数据和“适合当前本体”的限制把用户绑在一个场景上；动态数据只是模拟创建的过程，不能直接导入真实数据。
3. 演示本体太单薄：工厂数字孪生只有几个类型，血缘只有一条线，画不出复杂的链条，也接不上数据分析。人员主数据（Splink）这种演示对展示没有帮助。
4. 分析页面要能处理本体建模里创建的**所有**本体，而且用真实的本体对象，不是空壳模拟。

## 决定

**1. 一个通用导入器，不认识任何行业。** `backend/app/services/v2/data_import/` 把“一包表”变成一个本体：

| 步骤 | 做什么 |
|---|---|
| 读取 | 一个 `Bundle`：数据源（`Source`）、表（`Table`，分实体、事件、文件资产、关系表、过程表五种）、关系（`Link`）、计算表的 SQL 和列来源（`Derived`）、逐步载入的设置（`Replay`） |
| 识别 | `profile.finalize`：每列的平台类型；主键（声明的就检查，没声明的找“唯一、不为空、名字像键”的列）；关系（声明的就检查，没声明的按“列名指向对方的键 + 取值有 95% 以上在对方键里 + 至少 2 个不同值”推断，也就是包含依赖） |
| 创建 | 新建 `OntologyProject`（`build_mode = data_import`）；同名的要明确选“重新导入”才替换 |
| 发布 | 表结构写成 Auto Ontology 的交换格式，**走原来的候选审阅**：导入候选集 → 全部采纳（类型的中文名用“修改后采纳”）→ 一次发布成一个修订。每个类型、关系都带着它来自哪张表、哪些列的证据 |
| 规则 | 数据管理员对列写的规则（范围、取值集合、格式、必填）合进属性定义，数据健康检查自然读到 |
| 写入 | 行变成 `EntityInstance` 和图里的节点，对象编号 `<本体前 8 位>:<类型>:<主键>`；每个关系一条图边，关系表（多对多）变成边 |
| 核对 | 每个类型都有对象才算完成 |
| 血缘 | 最后一步自动生成这个本体的血缘；失败只报告，不让导入失败 |

走候选审阅而不是直接往表里插，是为了让导入和 AI 生成的候选在系统里是同一种东西：有证据、有修订、能在“AI 候选”里查到。

**2. 任何数据都能进。** 上传文件时：CSV、TSV、Excel、JSON、JSON Lines、Parquet 读成表（编码依次试 UTF-8、GB18030、Latin-1；只有一列的文件也能读；读不了的文件报“读不了 xxx：原因”，不抛内部错误）；图片、音频、视频、PDF、文档、点云等一律记成**文件资产对象**（`MediaAsset`：文件名、类型、大小、哈希，字节放在平台存储里，可预览）；ZIP 先展开。表里有一列装着文件名，就按名字和文件资产自动连起来。读完先给用户看识别出了什么（表、主键、关系、资产数），确认后才写入。

**3. 动态数据是真实数据的逐步载入。** 选一张事件表和排序列，先载入前 N 条，之后点“推进”或“自动播放”再载入下一批，对象和关系随之增长；游标存在导入记录里，刷新页面不丢。不再靠模拟创建。

**4. 五份不同来源、不同类型的演示数据**取代人员主数据（Splink）。数据文件在 `backend/examples/data_import/`，来源和许可见该目录的 `LICENSES.md`：

| 演示 | 来源 | 类型 | 规模 | 能看到什么 |
|---|---|---|---|---|
| 供应链订单履约（TPC-H） | DuckDB 自带的 TPC-H 生成器，不需要下载 | 关系型多表 | 12 个对象类型、13 个关系、7,498 个对象 | 八张业务表加四张计算表（供应商准时率、客户价值、订单履约、零件供应覆盖），血缘 31 个节点、48 条边、132 条列血缘；数据健康指出没达到业务目标的对象（供应商准时率、订单送达天数） |
| 出租车行程事件流（纽约 TLC） | NYC TLC 2019 年 1 月的 1 万次真实行程样本，加官方区域对照表 | 动态事件流 | 6 个类型；先载入 400 次行程，每次推进再来 400 | 逐步载入；真实的脏数据（乘客数为 0、车费为负），行程的 37 条期望里 4 条没通过 |
| 楼宇设备与传感时序（Brick） | BTS 数据集 Site B：Brick 格式的楼宇元数据加一年的传感器读数 | 时序 | 6 个类型、8,687 个对象、15 个作业的血缘 | 设备、空间、851 个测点（其中 49 个有读数）；血缘 51 个节点、71 条边；802 个测点没有数据，数据健康会指出 |
| 商品主数据合并（Abt-Buy） | 莱比锡大学的实体消歧基准：Abt、Buy 两家网店的商品目录和已知同款 | 多来源合并 | 3 个类型、2,332 个对象 | 实体消歧有标准答案可以打分；价格是必填但一半以上没有，数据健康会指出 |
| 豆叶病害照片 | Hugging Face 的 beans 数据集，每类取 20 张 | 多模态 | 4 个类型、126 个对象（60 张照片） | 照片作为文件资产，可以预览，和标签表按文件名连起来 |

三份需要下载的数据（Abt-Buy 压缩包约 131 KB、60 张照片约 3.45 MB、区域对照表约 12 KB）已经征得同意，SHA-256 在加载时核对。

**5. 血缘不再只有一条线。** 计算表的 SQL 和每一列来自哪些列，都记在导入记录里；本体的血缘生成器据此画出 数据源 → 读取 → 原始表 → SQL 计算 → 导入建模 → 对象类型 → 检查和消歧。

**6. 分析页面默认就是本体里的对象。** 数据健康、实体消歧、数据血缘、流水线演示打开就是“本体里的对象”：平台里每个本体都是一张卡片，选一个，再选一个对象类型（默认打开有对象、数量适中、有名称或编号这类属性的类型）；开源项目自带的示例文件放到“来源”切换的第二项。新增 `GET /api/v2/analysis/overview` 给首页和选择器用。大类型（超过 200 个对象）要分页读，卡片上写着预计的读取时间；只读账号不能固定快照，会得到明确的 403，而不是“找不到”。

**7. 实体消歧的自动设置不再只认人名。** 用五份数据反复试后改的地方：

- 比较方式新增三种：名称按共同词占比分级（`tokens`）；编号和型号（`code`）去掉符号后一致、或只是多了后缀才算吻合，**差一个字符是另一个东西，不当作相近**（颜色款的型号只差一位，按编辑距离会把它们错并）；金额按相对差距分级（`ratio`）。
- 新增“跨来源关联”（`link_across`）：有一列说明记录来自哪个来源（名字像 catalog、source，只有 2 到 4 个取值）时，只在不同来源之间配对，同一家网店里的不同款不互相比较。
- 自动设置会跳过：外键列（说明它属于另一个对象，常是从别的字段归出来的粗分类，放进来会把同一个证据算两遍）；两边都有值的记录对不足 15% 的列；两个取值的文本列。
- 先验用哪条规则估计，按它**实际会配出多少对**选（配出的对数不少于对象数的五十分之一、不多于对象数的三倍：太少，“假定能抓到七成真匹配”就估错了；太多，说明规则不够具体），选不到才退回按名字；训练用两个互不重叠的块，一个几乎全是匹配，一个能学其余字段。
- 没有能区分个体的属性（名称、编号、邮箱、电话、地址）的类型，抛出“不适用”（`NotApplicable`，接口 422，代码 `resolution_not_applicable`）。流水线遇到这样的类型不整体失败：数据健康和血缘照常跑，实体消歧一步标“已跳过”并写明原因。
- 最大的一组占全部对象的二十分之一以上时，结果里加一条提醒：多半是比较条件太宽，把不同的对象连成了一串。
- 词表比较改成每条记录只拆一次词，再做列表交集，Abt-Buy 的运行时间从 68 秒降到 7 秒。

**8. 平台改名“本体图谱平台”，首页改成大屏。** 大屏的数字全部来自 `/analysis/overview`：本体、对象类型、对象、关系类型的数量，各本体的对象数，当前本体的类型关系图，数据健康通过率，最近的分析，以及“数据源 → 对象类型 → 对象 → 关系类型 → 血缘作业 → 分析运行”的数据流向。侧栏的“数据源”不再依赖“当前本体”，成为独立的页面 `/sources`（本体详情的“数据源”页签里是同一个页面）。旧的三个专用导入器收在“专用格式的导入器”里，不再是主入口。

## 结果

在 p4int 上五份数据各自导入 1 到 3 秒，在“本体总览”“对象类型”“数据模型”里完整可见（TPC-H 在浏览器里核对过：12 个类型、13 种关系、7,498 个对象、16,089 条边）；对每个有对象的类型都跑过数据健康、实体消歧（适用的）、流水线，对每个本体生成了血缘，没有报错。Abt-Buy 的实体消歧：2,173 个商品归并成 1,624 个实体（真实 1,081 个），精确率 0.83，召回率 0.48，F1 0.61。

## 不要照搬 / 存疑

- **Abt-Buy 的召回率只有一半。** 约五分之一的商品名称里没有型号，只能靠名称，模型不敢下结论（概率落在 0.4 到 0.5 之间）；同款不同色的商品共用型号前缀，会少量错并。这是诚实的结果，“逐对解释”里能看到每一对为什么被连或没被连。
- **实体消歧只在有名称或编号的类型上有意义。** TPC-H 的客户、供应商、零件名称是 `Customer#000000001` 这类带序号的，没有真重复，结果是“没有找到重复”；Brick、出租车的大多数类型直接标“不适用”。
- **读大类型慢。** 7,350 个对象的观测类型读一遍约 16 秒；多于 10,000 个对象的类型只读前一部分。演示数据都压在 1 万个对象以内。
- **一次最多导入 50 个对象类型和关系；同一时间只跑一个导入。** 删除本体不能撤销，也只有有权限的账号能做。
- **逐步载入的数据要重新读取原始文件。** 内置演示从目录重新加载，上传的文件从平台存储里取回；存储里的文件被清理后就推不动了。
- **没有沿用的东西**：`seed_person_master_demo.py` 和“人员主数据（Splink 演示）”本体已删除；开源项目自带的三份示例文件（出租车、fake_1000、Marquez）仍在“来源”切换的第二项里。
